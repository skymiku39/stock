# 券商實際成交驗收計畫（草案，待核准）

對應 issue #38。狀態：**草案，尚未核准，任何限制都還沒有解除。** 這份文件只是計畫；核准前不執行任何一步。

原則（2026-11-16 使用者決定）：真實委託由使用者本人送出。Claude 與 subagent 不送出真實委託，只準備計畫、檢查清單與事後對帳。

## 一、要驗證什麼

模擬環境已經驗過流程（`simulation_check` 的 local 六個情境與 shioaji 模擬盤），沒驗過的是「真實券商端的行為是否和程式的假設一致」：

1. 零股限價單（盤中零股、LMT、ROD）送出後，委託回報與成交回報的欄位和時間。
2. 掛著不成交的零股限價單，取消後券商端確實撤單，沒有殘留委託。對應程式的 `SMILE_ORDER_TIMEOUT_SECONDS`（預設 120 秒）。
3. 部分成交時，已成交與未成交數量的回報方式。
4. 成交後的實際手續費、證交稅、交割金額，和 `trade_cost` 的計算是否一致（特別是零股最低手續費）。
5. 成交後券商端的持倉與程式記錄的持倉一致。

不在範圍內：策略有沒有獲利（那是 #19 的事）、整張委託、當沖。

## 二、目前擋住真實委託的機制

盤點日期 2026-11-17，以程式碼為準。

| 層 | 位置 | 作用 | 能否只改設定解除 |
|---|---|---|---|
| `SIMULATION` 預設 true | `src/bot/config.py:39` | 登入模擬環境 | 可以（`.env`） |
| `RUN_MODE` 預設 watch | `src/bot/config.py:20`、`src/bot/broker.py:398` | 非 trade 時 `place_order` 直接不送 | 可以（`.env`） |
| 當沖封存 | `src/bot/archive_status.py:13`、`src/bot/main.py:112` | trade 且非模擬時拒絕啟動 | 可以（`DAY_TRADING_UNFREEZE`） |
| 微笑策略啟動閘門 | `src/bot/main.py:109` | 微笑策略在 trade 且非模擬時拒絕啟動 | **不行，寫死在程式裡** |
| 微笑策略建構檢查 | `src/bot/strategy_smile.py:21` | 同上，建構時拋錯 | **不行** |
| 微笑策略每個 tick 的檢查 | `src/bot/strategy_smile.py:203` | 券商連線不是模擬就拋錯 | **不行** |
| 券商層 `simulation_only` | `src/bot/main.py:160`、`src/bot/broker.py:99`、`:394` | 微笑策略一律只允許模擬登入與模擬下單 | **不行** |
| Kill Switch | `src/bot/risk_guard.py:253` | 檔案存在就不進場 | 執行期開關，不是解除項目 |

兩個重點：

- **微笑策略沒辦法只靠改設定送出真實委託**，有四處寫死的檢查。要讓它送真實委託就必須改程式。
- 文件與程式不一致：`docs/archive/day-trading.md` 只寫用 `DAY_TRADING_UNFREEZE=true` 解除封存，但程式裡把 `DAY_TRADING_ARCHIVED` 設成 false 也會解除（`src/bot/archive_status.py:21`）。驗收前後都要確認這兩個設定的值。

## 三、兩種做法

### 做法甲：使用者用券商自己的 App 手動下單（建議）

不經過本專案的程式，所以**不需要解除任何限制，也不需要改程式**。

- 使用者在券商 App 送出零股限價單，完成第四節的五個情境，截圖或匯出委託與成交明細。
- Claude 事後把這些明細和程式的假設逐項比對：檔位、回報欄位、手續費與稅的算法、取消後的狀態。
- 能驗證：第一節的 1、2、3、4，以及 5 的券商端部分。
- 不能驗證：程式自己送單、自己收回報、自己逾時取消的整條路徑在真實環境是否正常。這一段目前只在模擬盤驗過。

### 做法乙：用程式送真實委託

需要改程式並解除多層限制，風險明顯較高。

- 要新增一個只給驗收用的工具（類似 `oddlot_test`，但連正式環境），一次只送一筆、金額寫死上限、每一步要使用者在終端機輸入確認。不改微笑策略本身的四處檢查。
- 由使用者本人在自己的終端機執行；Claude 不執行。
- 要解除：`SIMULATION`、`RUN_MODE`、當沖封存三層，驗收後逐層恢復。
- 能驗證做法甲驗不到的那一段，但只限於這個工具的下單路徑，不等於微笑策略的完整流程。

建議先做甲。甲的結果如果和程式的假設都一致，再決定乙有沒有必要。

## 四、驗收情境（做法甲）

每個情境都用零股、限價、ROD。標的與金額見第五節。

| 編號 | 操作 | 要記錄的內容 | 通過標準 |
|---|---|---|---|
| A1 | 以低於市價約 3% 的價格掛買單，等 3 分鐘 | 委託回報的欄位、狀態 | 委託存在、未成交 |
| A2 | 取消 A1 的委託 | 取消回報、取消後的委託狀態 | 委託狀態為已取消，沒有殘留 |
| A3 | 以接近賣一的價格掛買單，等到成交 | 成交回報、成交價、成交時間、是否分次成交 | 成交股數等於委託股數 |
| A4 | 次一交易日或當日，以接近買一的價格掛賣單賣出 A3 的部位 | 同上 | 持倉歸零 |
| A5 | 交割後取得對帳單 | 手續費、證交稅、交割金額 | 與 `trade_cost` 的計算相差不超過 1 元 |

檔位要符合程式的假設（`src/bot/smile_execution.py:11`）：10 元以下 0.01、10～50 元 0.05、50～100 元 0.1、100～500 元 0.5、500～1000 元 1、以上 5 元。任何一筆委託被券商以檔位不符退回，就記錄下來。

## 六、中止條件

發生下列任何一項就停止，不繼續下一個情境：

- 出現不是自己送出的委託。
- 委託或成交回報的數量、價格與送出的不一致。
- 取消後委託仍然存在，或券商端持倉和預期不一致。
- 金額超過核准的上限。

停止後：使用者在券商 App 取消所有未成交委託，確認持倉，再把情況記下來。

## 七、回復步驟

做法甲沒有解除任何限制，驗收結束只需確認：

- 券商端沒有未成交委託。
- 券商端持倉符合預期（A4 完成後應為零）。
- 專案的 `.env` 沒有被動過：`uv run stock-preflight --no-login` 顯示仍為模擬、觀察模式、封存中。

做法乙若經核准，回復步驟另訂，至少包含：逐層把 `SIMULATION`、`RUN_MODE`、`DAY_TRADING_UNFREEZE`、`DAY_TRADING_ARCHIVED` 設回原值，用 `stock-preflight --no-login` 確認，並確認兩個 Kill Switch 檔案（`data/.kill_switch`、`data/simulation/data/.kill_switch`）的狀態。
